# 分层整理（layer consolidation）

一次成功的整理 = **取证基线 → 规则设计 → 提案登记 → 分批实施 → 基线对照验收**。三条核心纪律：

1. **规则先于枚举**——放置规则决定文件去哪，不逐文件拍脑袋；规则要能回答"下一个新文件放哪"。
2. **平铺与内联是默认**——建组、外移都必须过阈值；分类系统的头号失败模式是变成倾倒场。
3. **行为保持是常态**——整理不改行为；预期例外必须显式写进提案并给出方向（修 bug 而非顺手改）。

## 何时不用

- 只是重命名几个文件、挪一两个组件：Direct 轨直接做，不走本流程。
- 目标是改行为/加功能：那是 feature 提案，整理至多作为前置批次。
- 缺少架构判断依据时：先读用户级技能 `codebase-design`（deep module、leverage、locality 的判定语言），本技能的抽取判定建立在它之上。

## 第一步：取证基线

动手前用 grep/wc 实测并记住数字，全部写进提案的 Note。没有基线的整理无法验收，也无法回答"值得吗"：

```bash
# 重复编排的规模
grep -rn 'catch (e: any)' src/pages src/components | wc -l
# 跨层引用（散落的硬证据）
grep -rn "from './" src/pages/*.tsx | grep -E "from '\./[A-Z]"
# 体量分布
wc -l src/pages/*.tsx src/components/*.tsx src/lib/*.ts | sort -rn
# 内联组件盘点
grep -cE '^(export )?function [A-Z]|^const [A-Z][A-Za-z]+ = ' src/pages/*.tsx
```

四类基线缺一不可：**重复计数**（按文件分布）、**跨层引用**（散落的硬证据）、**体量分布**（超载文件）、**内联组件清单**（归位对象）。

## 第二步：设计放置规则

规则成对出现：一条"必须移"、一条"必须留"。参考模板（组件 R 系 + lib L 系，按目标库取舍裁剪）：

| # | 规则 | 为什么 |
| --- | --- | --- |
| R1 | 跨页面/跨层消费的组件 → 必须 `components/`；跨页 import 清零 | 组件被迫定义在别人的页面文件里，是散落最硬的证据 |
| R2 | 页面私有、体量小、所在文件不超载 → 留内联 | 内联即最高局部性；全搬出去是碎片化，components/ 会变倾倒场 |
| R3 | 页面私有但构成页面主要渲染体、所在文件超载 → `components/<domain>/` | 页面文件回归"数据编排 + 组装"；域目录保证可检索 |
| R4 | lib 里的渲染面留 lib | "含 JSX"不是搬进控件层的理由——引擎的渲染出口还是引擎（转场、Provider） |
| L1-L4 | lib 建组阈值：**≥3 个文件共享同一关注点才建组**，否则平铺 | 门面文件（import 面最大的入口，如 api 客户端）永远留根；大引擎单文件留平铺 |

设计规则时逐条自问：**下一个人写一个新文件，这条规则能告诉他放哪吗？**不能就重写。同时列出"明确不做的"（不抽的脚手架、不统一的行为、不动的小文件）——这一节和"要做的"同样重要。

**抽取 vs 文档化**的判定（deep module 视角）：

- **抽**：N 处近逐字重复且行为一致（如 try→请求→刷新→提示 编排 42 处）。抽取即加深，一次收敛。
- **只文档化**：习语相同但细节各有道理、且细节带并发防护（如多种乐观更新模式）。强行统一成 options-bag = 浅模块。把适用场景与防护要求写进 `docs/` 工程约束页。
- **补齐式收敛**：存在共享不变式但只有一份副本实现（如"refetch 后重灌未脏草稿"4 份缺 3）。先逐处核对行为差异，hook 只收敛真正共享的部分，分歧处保留原样；这是整理中唯一合法的行为变化，方向必须是修正。

## 第三步：登记提案

整理是 Noted 轨变更，按 `.agents/pipelines/WORKFLOW.md` 模板登记（本仓 Class 多为 `simplification`）：

- **Goal** 写可观察收益，不写"代码更整洁"这类不可验收的话。
- **Decision** 每条一个决定；放置规则表、拆分映射表（现文件 → 拆出文件）放这里；"不做的"单列一条。
- **Accept** 全部可观察：基线数字对照（"42 处收敛至 helper"）、清零断言（"跨页 import 清零"）、行为不变断言（"路由与用户可见行为不变"）、行数上限、检查命令全绿。
- **Note** 放基线数据、粒度判断依据、实施顺序建议，并链接参考实例（见下）。

## 第四步：分批实施

顺序有两个原则：**机械移动先行**（拆分、归位、分组是纯移动，先做掉——后续批次在目标结构上做，diff 更干净），**一次 import 风暴**（所有移动/改路径集中在同一批，不要分三次折腾全库 import）。

典型批次：机械拆分与归位 → 收敛 helper 逐处等价替换 → 逻辑抽出可测化（依赖注入时钟/IO，vitest 覆盖状态机）→ hook 收敛（先核对差异）→ 约定文档化。

每批之后跑仓库规定的检查（本仓：`pnpm check`、`pnpm test`、`pnpm build`、`npm run test:server`）。等价替换的判据是逐处对照旧代码的文案与回滚行为，不是"看起来一样"。

## 陷阱清单

- **barrel 抵消拆分**：拆完再留一个 re-export barrel，import fan-in 成本一点没降。要拆就全量改 import。
- **options-bag 是浅模块**：把 N 种行为不同的习语统一成带 8 个开关的 helper，接口比实现还复杂。
- **基线靠印象**：没跑 grep 就写"大量重复"，提案无法验收，也说服不了人。
- **倾倒场**：components/ 里堆满单处使用的私有小组件，比散落在页面里更糟——页面内联本身就是局部性。
- **顺手改行为**：整理途中看到"顺便能修"的 bug，记下来单独走 bug-fix，不要混进移动批次。
- **一次提案做两个方向**：整理是 simplification；发现的平台专项问题（如探测散布的最小修复可以顺带，全面治理）另立提案。

## 参考实例

本仓 `.agents/pipelines/proposals/simplification/2026-10-06-src-layer-consolidation.md` 是本方法论的完整实例：基线（42 处编排 / 3 处跨页 import / 24 个内联组件 / lib 20 个平铺文件）、R1-R4 与 L1-L4 规则、目录树、Accept 对照。设计与实施冲突时，以该提案的演进为准。
