# Vendored fork of tauri-plugin-system-components

This directory is a local fork of the crates.io crate
[`tauri-plugin-system-components`](https://github.com/sosweetham/tauri-plugin-system-components),
patched in via `[patch.crates-io]` in `src-tauri/Cargo.toml`. The shell's native
overlays (Liquid Glass tab bar, back button, top-bar action) are this plugin.

## Upstream baseline

| | |
| --- | --- |
| Crate | `tauri-plugin-system-components` |
| Version | 0.1.8 |
| Upstream commit | `0b05ec1ef8760bec2710d5e2a1ae64e78e76190e` |
| Licence / author | MIT, SoSweetHam |

The commit hash used to live in the crate-package artifact
`.cargo_vcs_info.json`; it is recorded here instead because that file (like the
rest of the packaging metadata) is not part of the source we maintain.

## Why a fork at all

Native controls float **above** the WebView and take no part in CSS
transitions, so entrance/exit animation and content tinting can only be done on
the native side. Upstream 0.1.8 has no such API, and the shell needs it:

- the back button / top-bar action must fade (or slide with the page) instead
  of popping in mid-transition;
- a glass button must be able to tint its glyph without recolouring its capsule;
- a control must be able to follow the **app** theme (light/dark), which may
  differ from the system appearance;
- the app must be able to fade a control out before removing it (removal itself
  is instant, so a hard cut would otherwise be visible).

## Delta against upstream 0.1.8

Everything below is **additive**: no upstream field, command or behaviour is
changed or removed. Keep it that way — the whole point of a thin delta is that
bumping upstream stays a mechanical replay rather than a semantic merge.

### Rust

| File | Change | Why |
| --- | --- | --- |
| `src/models.rs` | 6 new `ComponentProps` fields: `foreground`, `alpha`, `accessibilityLabel`, `appearAnimation`, `appearOffsetX`, `appearDuration`; new `SetAppearanceOptions` | carry the iOS-side affordances through the command payload |
| `src/commands.rs`, `src/lib.rs` | register the `set_appearance` command | app theme → native overlays |
| `src/mobile.rs` | `set_appearance` forwards to the Swift plugin (`run_mobile_plugin("setAppearance")`) | iOS implementation entry point |
| `src/desktop/mod.rs` | `set_appearance` is a no-op on macOS | macOS native chrome follows the system appearance; only the iOS overlays need the override |
| `build.rs` | `set_appearance` added to `COMMANDS` | generates its `allow-set-appearance` permission |
| `permissions/default.toml` | `allow-set-appearance` added to the default set | the app's capability grants `system-components:default`, so a command missing from the set is rejected at invoke time |

### iOS (`ios/Sources`)

| File | Change | Why |
| --- | --- | --- |
| `SystemComponentsPlugin.swift` | `SetAppearanceArgs`, `appearanceStyle`, `applyAppearance()` (applied on set **and** whenever an overlay is mounted), `setAppearance` entry point | UIKit otherwise follows the system appearance; overlays must follow the app theme instead |
| `Components/ComponentArgs.swift` | decode `foreground`, `alpha`, `accessibilityLabel`, `appearAnimation`, `appearOffsetX`, `appearDuration` | mirror of the Rust payload |
| `ComponentsOverlay.swift` | appear animation on create (`appearOffsetX` slides in with the page-transition curve, else spring fade + scale via `appearAnimation`); `alpha` fade in `update` | native controls cannot ride CSS transitions; removal is instant, so JS fades out first |
| `Components/ButtonComponent.swift` | `foreground` → `baseBackgroundColor`/`baseForegroundColor`/`tintColor`; SF Symbol tinting via `withTintColor(_:renderingMode: .alwaysOriginal)`; `accessibilityLabel` → `UIButton.accessibilityLabel` | iOS 26 glass configurations ignore `baseForegroundColor` for symbols; an icon-only button otherwise announces the SF Symbol's own name (`arrow.up.doc` reads as "Previous Page") |

### Repo hygiene on top of the vendored tree

- `permissions/autogenerated/**` and `permissions/schemas/schema.json` are
  **build outputs** (written by `tauri-plugin`'s build script on every build)
  and are git-ignored here. `permissions/default.toml` is hand-written and
  stays tracked.
- Packaging artifacts of the published crate were dropped: `.cargo-ok`,
  `Cargo.toml.orig`, the crate's own `Cargo.lock` (a path dependency uses the
  app's lockfile) and `.github/workflows/**` (nested workflows never run).
- Deliberately **not** pruned: upstream's surface the app does not use
  (native sheets, tab badges, show/hide tab bar, batched component updates,
  macOS window glass, the Android plugin, the unused component kinds). Removing
  it would turn an additive delta into a structural one and make every upstream
  bump a rewrite.

## Replaying the delta on a new upstream release

1. `scripts/plugin-fork-diff.sh` prints the current delta (it fetches the
   upstream crate from crates.io if the local cargo registry has no copy).
2. Bump the version in `Cargo.toml` and the baseline table above; run the script
   against the new version and check whether any of our delta already landed
   upstream — if it did, drop our implementation of it instead of replaying.
3. Re-apply whatever is still missing, file by file.
4. Record the new upstream commit hash (from the crates.io/GitHub release) in
   the baseline table.
5. Verify: `cd src-tauri && cargo test`, then an iOS build — the fork's Swift is
   compiled into the app (its identifiers are visible in the built binary), so a
   Swift-side mistake only shows up there.
